# Firebase

## Collections

| Collection | Owner field | Used by | Rule (`firestore.rules`) |
|---|---|---|---|
| `users/{uid}` | doc id | `UserProfileRepository` | owner only; body profile, snake_case |
| `user_tokens/{uid}` | doc id | `NotificationService` → functions | owner only (functions use the Admin SDK) |
| `crews` | `userId` (legacy `ownerId`) | crews | **read: any signed-in user**; create/update/delete: owner |
| `custom_characters` | `userId` | custom_character, duels | owner only |
| `planner` | `userId` | robin_knowledge | owner only |
| `workout_assessments` | `user_id` | zoro_workout, sanji_cooking | owner only; one doc per user per month (`month_year`) |
| `featuredCharacters` | — | home, one_piece | public read, no client writes (seeded with the Admin SDK) |

Any other collection has no `match` block and is denied to clients. Nami finances
are Hive-only — never add a Firestore collection for them without a spec.

## Security rules — current state

Owner-scoped since #25. Helpers in `firestore.rules`:

- `isSignedIn()` — `request.auth != null`.
- `isOwner(userId)` — signed in and `request.auth.uid == userId`.
- `createsOwn()` — `isOwner(request.resource.data.userId)`: a create must stamp the
  caller's uid (`IFirestoreService.createUserDocument` does this).
- `keepsUserId()` — an update cannot change `userId`.
- `crewOwner(data)` — `userId`, falling back to `ownerId` for crews created before
  `userId` existed.

Per collection: `read`/`delete` require `isOwner(resource.data.userId)`, `create`
requires `createsOwn()`, `update` requires owner + `keepsUserId()`.
`workout_assessments` applies the same pattern to `user_id`. `crews` is the one
deliberate exception: `allow read: if isSignedIn()` (public showcase for "list all
crews"), while update/delete use `crewOwner` and an update cannot change the owner.

- An unfiltered query over an owner-only collection is denied as a whole — e.g.
  `getAllCustomCharacters()` — Duels uses `getUserCustomCharacters()` for that reason.
  Query with `where('userId', isEqualTo: uid)` (`getUserDocuments`).
- Any new collection: add a `match` block with the same owner-scoped
  `read`/`create`/`update`/`delete` — never a blanket `allow read, write`.
- **Field validation (SEC-9):** every write is also checked field by field — an
  allowed-keys list per collection (`profileKeys()`, `crewKeys()`, ...), types
  (`number`, never `float`: web stores whole doubles as integers), string/list
  size caps (image fields are URLs ≤ 4096 chars, so inline data URIs are
  refused), `serverTimestamp()` fields must equal `request.time`, and client
  timestamps (`workout_assessments`) must be within a day of it. Creates check
  `keys()`; updates check only `diff(resource.data).affectedKeys()`, because old
  documents still carry legacy fields.
- **Adding or renaming a field the app writes** means updating that collection's
  key list in `firestore.rules` and the payload builder in
  `tool/firestore_rules_test/rules.test.mjs` — otherwise the write is denied in
  production. Run the suite locally with `npm test --prefix tool/firestore_rules_test`
  (needs Java); CI runs it on every PR.
- Rules deploy works on the free Spark plan (`firebase deploy --only firestore:rules`).
- Do not loosen or tighten rules for existing collections without telling the user;
  rules changes need `firebase deploy --only firestore:rules` to take effect.

## Cloud Functions (`functions/src/index.ts`)

TypeScript, Firebase Functions v2, Node 22, timezone `America/Sao_Paulo`. Every
function reads FCM tokens from `user_tokens`, sends multicast, prunes invalid tokens.

| Function | Trigger |
|---|---|
| `sendNamiMonthlyNotification` | cron `0 9 28-31 * *`, sends only on the last day of the month |
| `sendZoroWorkoutNotification` | 18:00 Mon–Sat |
| `sendSanjiCookingNotification` | 12:00 daily |
| `sendCustomNotification` | callable |
| `testNotification` | HTTP |

Sends prune a token only for `registration-token-not-registered` /
`invalid-registration-token`, and log it masked. `testNotification` (admin only)
sends to the caller's own token, never to other users.

Deploy with `cd functions && npm run deploy` — only when the user asks; it hits the
real project. **The project has no billing account (Spark):** Functions cannot be
deployed (or redeployed) until billing is enabled, and the functions above were
deployed before that — check in the console whether they still run. Do not
propose Functions, Secret Manager or Cloud Scheduler for new work.
